# Support Ticket System — Design

Date: 2026-07-26
Status: Approved by user, ready for implementation planning

## Context

Second of three follow-up features chosen by the user this session, after multi-tier subscription plans (shipped) and before system health monitoring (not started). Replaces the "Tickets en cours" panel in `frontend/src/pages/PlatformAdmin/PlatformAdminPage.tsx`, currently a disabled "bientôt disponible" placeholder (see `.planning/banani/platform-admin.md`) — there is no ticket infrastructure anywhere in this codebase today.

## Decisions (confirmed with the user via AskUserQuestion)

1. **Ticket creators**: clinic `admin` role only — matches the existing pattern for billing/staff management, which are also admin-gated.
2. **Clinic-side UI location**: a new 5th sub-tab "Support" in `SettingsPage.tsx`, alongside Abonnez-vous/Informations Clinique/Gestion des Utilisateurs/Sécurité.
3. **Reply model**: single message + status only, not a threaded conversation. The admin submits one message describing the issue; the SaaS operator (via Platform Admin) can only change status and optionally attach a resolution note. No back-and-forth thread — real conversation happens outside the app (email/WhatsApp) if needed. This keeps the feature a tracker, not a chat system.
4. **Ticket fields**: subject + category + message (not just subject + message) — a category lets the operator triage at a glance once multiple clinics have open tickets.
5. **Status-change notifications**: yes — the clinic admin gets an email when the operator changes a ticket's status, reusing the existing `backend/utils/mailer.js` three-tier fallback (Resend → SMTP → console), the same mechanism already built for subscription renewal reminders.

## Architecture

One new table, no separate messages table (per decision 3 — threading would need one, but isn't in scope). Clinic-scoped like every other table in this app (`clinic_id` on every row, filtered by `.eq('clinic_id', req.user.clinicId)` in every clinic-side query) — `backend/routes/platform.js` is the sole existing exception that reads across clinics, and this feature's platform-side endpoint follows that same established exception, not a new one.

### Schema (`backend/supabase_schema.sql`)

```sql
CREATE TABLE support_tickets (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  clinic_id BIGINT REFERENCES clinics(id) ON DELETE CASCADE NOT NULL,
  created_by BIGINT REFERENCES users(id) ON DELETE SET NULL,
  subject TEXT NOT NULL,
  category TEXT NOT NULL DEFAULT 'general' CHECK (category IN ('facturation', 'bug', 'general', 'autre')),
  message TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'open' CHECK (status IN ('open', 'in_progress', 'resolved', 'closed')),
  resolution_note TEXT,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  updated_at TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_support_tickets_clinic ON support_tickets(clinic_id);
```

`created_by` is `ON DELETE SET NULL` (not CASCADE) so a ticket survives if the creating admin's account is later deactivated/deleted — matches the pattern already used for `deposits.resolved_by`.

This is a **new table**, so — same schema-drift constraint as every other change this session — it must be created by hand in the Supabase SQL Editor before the feature works live; it will be bundled into the same pending-migrations list as the plan columns.

### Backend endpoints

**Clinic side** — new routes in `backend/routes/settings.js`, admin-only via the existing `checkRole(['admin'])`:
- `POST /api/settings/tickets` — body `{ subject, category, message }`. Inserts a row with `clinic_id: req.user.clinicId`, `created_by: req.user.userId`, `status: 'open'`. Writes an `activity_logs` row (`TICKET_CREATE`), matching every other mutation in this app.
- `GET /api/settings/tickets` — lists this clinic's own tickets, newest first. No role restriction beyond admin (same as the other billing/staff endpoints in this file).

**Platform side** — new routes in `backend/routes/platform.js`, already gated by `router.use(auth, superAdminOnly)`:
- `GET /api/platform/tickets` — every ticket across every clinic, joined to clinic name (same join pattern `platform.js` already uses for `subscription_payments`/`users`), optional `?status=` query filter.
- `PUT /api/platform/tickets/:id` — body `{ status, resolutionNote? }`. Updates `status`, `resolution_note`, `updated_at`. After a successful update, looks up the ticket's `clinic_id` → the clinic's active `admin` user (same lookup pattern as `backend/routes/cron.js`'s renewal-reminder job) and sends a status-change email via a new `sendTicketStatusEmail()` in `mailer.js`. The email send is fire-and-forget (doesn't block the response, logged on failure) — same non-blocking pattern already used for the registration confirmation email in `auth.js`.

### Frontend

**`SettingsPage.tsx`** — new `activeSubTab` value `'support'`, tab button "Support" added to the existing pill row (after "Sécurité"). Content: a create-ticket form (subject text input, category `<select>` with options Facturation/Bug technique/Question générale/Autre — mapping to `facturation`/`bug`/`general`/`autre`, message textarea, submit button) above a list of the clinic's own tickets (subject, category badge, status badge, created date, resolution note if present) fetched from `GET /settings/tickets`. Follows this file's existing conventions — inline `style={{}}` + shared `.btn`/`.card`/`.badge-*` classes, no new abstractions.

**`PlatformAdminPage.tsx`** — the existing "Tickets en cours" placeholder panel (currently static text) becomes a real table: subject, clinic name, category, status (with a `<select>` to change it inline), created date, and an expandable row revealing a resolution-note textarea (submits together with the status change in the same `PUT /platform/tickets/:id` call). Status filter pills (Tous/Ouvert/En cours/Résolu/Fermé) above the table.

## Error handling

- `POST /settings/tickets`: 400 if subject/category/message missing, or category not in the allowed set.
- `PUT /platform/tickets/:id`: 400 if status not in the allowed set; 404 if ticket doesn't exist. Email failure does not fail the request (logged, same as other non-blocking email sends in this app).
- No new payment/webhook surface, no new schema-drift risk beyond the one new table (which is a lower risk than an `ALTER TABLE` on an existing populated table, since it starts empty).

## Testing / verification plan

No automated test suite in this repo (confirmed in CLAUDE.md). Verification will be: `npm run build` + `npm run lint` (frontend), a smoke test creating a ticket as admin, verifying it appears in Platform Admin's ticket list, changing its status, and confirming (via console-logged email in dev, since Resend is configured but a live inbox isn't guaranteed available) that the reminder email fires. Same verification pattern used for every other feature shipped this session.

## Out of scope (explicitly deferred, not forgotten)

- Threaded replies / attachments / read receipts — decision 3 explicitly scoped this out.
- Ticket creation by non-admin clinic staff — decision 1 explicitly scoped this out.
- System health monitoring — the third follow-up feature, a separate project with its own design.
