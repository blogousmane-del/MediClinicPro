# Platform Admin — Rapports, Sécurité, Config. système — Design

Date: 2026-08-06
Status: Approved by user, ready for implementation planning

## Context

`frontend/src/pages/PlatformAdmin/PlatformAdminPage.tsx` renders three sidebar
entries as disabled with a "BIENTÔT" badge: **Rapports**, **Sécurité**,
**Config. système**. The user reported them as broken. They are not broken —
they were never built. The comment at `PlatformAdminPage.tsx:263` says so
explicitly: no reporting, security, or system-config backend exists.

This spec covers all three in one document, at the user's explicit request
after being warned that they are three independent subsystems and that a
single spec would be large. The implementation plan must therefore split them
into independently shippable tasks.

### What already exists to build on

- `activity_logs` — `clinic_id` (NOT NULL), `user_id`, `action`, `details`,
  `ip_address`, `created_at`. 30 distinct action values are written across
  `backend/routes/*.js`, including `LOGIN` and `LOGIN_GOOGLE`.
- `subscription_payments` — `clinic_id`, `plan`, `months`, `amount`,
  `provider`, `amount_usd`, `status`, `created_at`, `paid_at`.
- `clinics` — `plan`, `subscription_status`, `subscription_expires_at`,
  `unlimited_staff`, `suspended_by_platform`, `created_at`.
- `users` — `role`, `active`, `password_set`, `created_at`.
- `patients` — `archived`, `created_at`. `consultations` — `date_time` and
  **no `created_at`**. `support_tickets` — `category`, `status`, `created_at`.
- `backend/middleware/superAdminOnly.js` — the existing gate, reused as-is.
- `backend/utils/plans.js` — `PLANS`, the single source of truth for prices
  and limits.

### Decisions taken during brainstorming

1. All three sections in one spec (user's choice over a phased approach).
2. Config. système = read-only inspector **plus** a small set of safe editable
   settings.
3. Two new tables are acceptable; the user runs the SQL by hand in the
   Supabase SQL Editor (this repo has no DDL access — see CLAUDE.md).
4. Rapports has two tabs, Revenus and Adoption, Revenus shown by default.
5. Charts are hand-rolled inline SVG. No charting dependency: Platform Admin
   ships in the same bundle every clinic downloads, often on mobile
   connections in Côte d'Ivoire.

## Architecture

`backend/routes/platform.js` is already 591 lines and
`PlatformAdminPage.tsx` 1126. Adding three sections in place would produce
~1200 and ~2200 line files. Instead:

**Backend** — three new route modules, each mounted in `server.js` under
`/api/platform` and gated by the existing `superAdminOnly`. `platform.js` is
not modified.

```
backend/routes/platform-reports.js    GET /reports/revenue, /reports/adoption
backend/routes/platform-security.js   GET /security/audit, /security/logins, /security/posture
backend/routes/platform-config.js     GET /config, PUT /config
```

**Frontend** — the three `comingSoonItems` entries become real sections.
`PlatformAdminPage.tsx` keeps only the shell and navigation and shrinks as
each section moves out.

```
frontend/src/pages/PlatformAdmin/sections/ReportsSection.tsx
frontend/src/pages/PlatformAdmin/sections/SecuritySection.tsx
frontend/src/pages/PlatformAdmin/sections/SystemConfigSection.tsx
frontend/src/pages/PlatformAdmin/components/BarChart.tsx     (~50 lines SVG)
frontend/src/pages/PlatformAdmin/components/DonutChart.tsx   (~40 lines SVG)
```

Charts must render correctly in both light and dark themes, using the existing
HSL custom properties from `index.css` rather than hardcoded colours.

Aggregation follows the pattern already used by `GET /api/platform/overview`
(`platform.js:60-68`): plain `select`s, then aggregate in JS with `Map`s.

## Data model

### New table 1 — `login_failures`

Failed logins cannot go into `activity_logs`: its `clinic_id` is `NOT NULL`,
and a failure against an unknown email has no clinic.

```sql
CREATE TABLE login_failures (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  email TEXT NOT NULL,              -- normalised; may match no account
  clinic_id BIGINT REFERENCES clinics(id) ON DELETE CASCADE,  -- NULL when the email is unknown
  reason TEXT NOT NULL,             -- unknown_email | bad_password | inactive_account
  ip_address TEXT,
  created_at TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_login_failures_created ON login_failures(created_at DESC);
CREATE INDEX idx_login_failures_ip ON login_failures(ip_address, created_at DESC);
```

- **Failures only.** Successful logins are already in `activity_logs`
  (`LOGIN`, `LOGIN_GOOGLE`); duplicating them would double write volume and
  teach nothing.
- **Never store the attempted password**, nor a hash or length of it. Email,
  IP and reason only.
- **90-day purge**, added to the existing daily cron at `/api/cron`. Without
  it the table grows without bound.

### New table 2 — `platform_settings`

```sql
CREATE TABLE platform_settings (
  key TEXT PRIMARY KEY,
  value TEXT,
  updated_by BIGINT REFERENCES users(id) ON DELETE SET NULL,
  updated_at TIMESTAMPTZ DEFAULT NOW()
);
```

| Key | Effect | Default |
|---|---|---|
| `starter_trial_days` | Overrides `trialDays: 7` (`plans.js:10`), read at registration | `7` |
| `maintenance_message` | Banner shown to all clinic users; empty disables it | empty |

Deliberately **not** in this table:

- **Plan prices and staff limits.** `PLANS` stays the single source of truth.
  A typo in a mutable store would break billing for every clinic at once.
- **`SUPER_ADMIN_EMAILS`.** It is the authentication boundary of the console
  itself; making it editable from inside the console it protects creates a
  privilege-escalation loop. It stays an environment variable.

Both tables are additions to `supabase_schema.sql` and must be run by hand.
Until then, every route that touches them degrades to a clear message (see
Error handling).

## Rapports

### `GET /api/platform/reports/revenue`

| Block | Computation | Render |
|---|---|---|
| Monthly revenue, 12 months | `SUM(amount)` over `subscription_payments` where `status='paid'`, grouped by month of `paid_at` | SVG bars |
| Monthly recurring revenue | Sum of `PLANS[clinic.plan].price` over clinics with `subscription_status='active'` on a paid plan | Large figure |
| Plan distribution | Clinic count by `plan` | SVG donut |
| Renewals within 30 days | `clinics.subscription_expires_at` between now and +30d | Table, by due date |
| Expired, not renewed | `subscription_expires_at` in the past, status not active | Table |
| **Stuck payments** | `subscription_payments` `status='pending'` older than 1 hour, plus this month's `failed` | Table |
| Provider mix | Count by `provider` over paid rows | SVG donut |

Two accuracy constraints, to be reflected in the UI copy:

**Recurring revenue is not the sum of collections.** Subscriptions are prepaid
for 1–12 months, so collecting 12 months in January does not make January a
174 000 FCFA recurring month. MRR is therefore derived from active clinics and
their plan, not from payments. Both figures appear on screen with a one-line
explanation of why they differ.

**Stuck payments are a deliberate feature, not filler.** A `pending` row older
than an hour means a provider webhook never arrived — the "money taken,
nothing credited" case that the misconfigured PayPal webhook would have caused
in production.

### `GET /api/platform/reports/adoption`

| Block | Computation |
|---|---|
| Active vs dormant clinics | A clinic is active if it has at least one `activity_logs` row in the last 30 days |
| Volume per clinic | Counts of `patients`, `consultations`, active `users` |
| New clinics per month | `clinics.created_at`, 12 months, SVG bars |
| Roles actually filled | Count of active `users.role` across all clinics |
| Tickets by category and status | `support_tickets` |

Two limits, to be stated in the UI rather than discovered later:

**There is no per-module usage tracking in this codebase.** Nothing records
"the pharmacy screen was opened". The role breakdown is a *proxy* — a clinic
with an active `pharmacist` probably uses the pharmacy — not a measurement.
It must be labelled as such, never presented as telemetry. This follows the
existing repo rule against fabricated stats (see CLAUDE.md, Banani section).

**`consultations` has no `created_at`**, only `date_time`. Consultation trends
are therefore keyed on appointment date, not entry date — a real difference
for a clinic that enters records late.

### Known scale limit

Fetching all `patients` and `consultations` rows to count them in JS matches
the existing `/overview` code and is fine at current scale. It will degrade
somewhere in the tens of thousands of rows. The replacement is a Postgres RPC
doing the aggregation server-side. Recorded here as identified debt, not as a
surprise.

## Sécurité

### `GET /api/platform/security/audit`

The cross-clinic `activity_logs` feed, filterable by clinic, user, action type
and date range, paginated.

Super-Admin actions (`PLATFORM_*`) are the one place where a row's `clinic_id`
and the acting `user_id`'s own clinic deliberately diverge. The view marks
them distinctly — otherwise they read as if the clinic had modified itself.

### `GET /api/platform/security/logins`

Backed by `login_failures`. Recent failures, most active IPs, most targeted
emails, and the signal that matters: **more than N failures from one IP within
an hour**, which separates a forgotten password from credential stuffing.
N is a module-level constant, initially 10.

This requires a change in `backend/routes/auth.js` to record the three failure
reasons (`unknown_email`, `bad_password`, `inactive_account`) on the
password login path (`POST /auth/login`) only. `POST /auth/google` is out of
scope: its failures are Google token rejections, not credential guesses
against this app, and mixing them into the same table would blur the
brute-force signal. Two non-negotiable guardrails:

- **The write is fire-and-forget inside a try/catch.** If the table is missing
  or Supabase fails, login must still work. A security log never breaks
  authentication.
- **The client-facing error stays `"Identifiants invalides."` in all three
  cases.** The precise reason is recorded server-side and never revealed,
  otherwise the endpoint becomes an oracle for which emails exist.

### `GET /api/platform/security/posture`

Read-only state of the platform's defences: suspended clinics, deactivated
accounts, clinics with no active admin (a clinic locked out of itself),
Google-only accounts with `password_set = false`, and the number of configured
Super Admins.

Surfaced prominently: **whether rate limiting is backed by Upstash Redis or
the in-memory fallback.** In memory on Vercel it is per-instance and resets on
every cold start, so it is close to nonexistent — a real and currently
invisible weakness.

## Config. système

### `GET /api/platform/config`

| Block | Reported |
|---|---|
| Payments | Bictorys, PayTech, PayPal — configured or not, via each `isConfigured()` |
| PayPal | Effective mode, **and whether `PAYPAL_MODE` is a recognised keyword** |
| Email | Which of the three is active: Resend, SMTP, or console fallback |
| Rate limiting | Upstash Redis or in-memory fallback |
| Google Sign-In | Active or inert |
| Cron | `CRON_SECRET` set or not |
| URLs | `API_PUBLIC_URL`, `APP_URL` |
| Database | Supabase connectivity, tested with a trivial query |
| Plans | Effective prices and limits read from `PLANS`, read-only |

**Absolute rule: this route never returns a secret value.** Booleans
("set" / "blank") plus the public URLs only. No key, no key prefix, no length.
`superAdminOnly` guards the route, but a route that exposes nothing cannot
leak anything even if the guard were bypassed.

This page is what would have shown in seconds what took an hour to find on
PayPal: an unrecognised `PAYPAL_MODE` and live credentials pointed at sandbox.

### `PUT /api/platform/config`

Updates the two keys. Server-side validation, one `activity_logs` row per
change:

- `starter_trial_days` — integer, 1 to 90. Read by `auth.js` at registration,
  falling back to `PLANS.starter.trialDays` when the table is missing or the
  value unreadable. Never changes a trial already in progress.
- `maintenance_message` — plain text, 280 characters max, empty disables.
  Rendered as text, never as HTML.

The maintenance banner reaches the frontend through `GET /auth/me`, already
called on mount by `AuthContext` — no new network call, no polling.

## Error handling

One rule everywhere: **a missing table produces a clear message, never a
500.** A `42703` (missing column) or `PGRST205` (missing table) on
`login_failures` or `platform_settings` renders "Migration à exécuter" with
the SQL to copy. This is the number one failure mode in this repo (see
CLAUDE.md, schema drift) and is designed for rather than discovered.

All user-facing strings are in French, matching the rest of the app.

## Testing

Extends the `node --test` suite added on 2026-08-04, same pattern: real route
modules mounted on a throwaway Express app, with only `database.js` and
`middleware/auth.js` replaced through the `require` cache.

- `platform-security.test.js` — a failed login writes a row; a failing insert
  does not break login; the client message is identical for all three reasons.
- `platform-config.test.js` — the response contains no secret value;
  `starter_trial_days` out of range is rejected; a missing table yields a
  message rather than a 500.
- `platform-reports.test.js` — recurring revenue is not confused with the sum
  of collections; stuck payments are surfaced.

## Out of scope

- Per-module usage telemetry (no instrumentation exists; adding it is its own
  project).
- Editable plan prices and limits.
- Exporting reports to CSV or PDF.
- Postgres RPC aggregation (recorded above as identified debt).
- Chargeback handling for `PAYMENT.CAPTURE.REVERSED`, still unimplemented and
  unrelated to these sections.
