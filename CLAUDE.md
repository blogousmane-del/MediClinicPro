# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

MediClinic is a multi-tenant clinic management SaaS for small/medium clinics in Côte d'Ivoire, with three subscription tiers — Starter (free, 7-day trial), Clinique (9 000 FCFA/month), Hôpital (14 500 FCFA/month), see Multi-tier subscription plans below. UI, error messages, and domain terms are in French — keep new user-facing strings in French to match the existing app.

Monorepo with three parts:
- `backend/` — Express REST API
- `frontend/` — React 19 + TypeScript + Vite SPA
- `api/index.js` — thin Vercel serverless wrapper that re-exports `backend/server.js` for `/api/*` requests in production

## Commands

Run from the repo root (`package.json` orchestrates both apps):
```bash
npm run backend         # node backend/server.js (port 5000)
npm run frontend        # vite dev server for frontend/ (port 5173)
npm run dev              # starts both concurrently (Windows/PowerShell only)
npm run build:frontend  # tsc -b && vite build for frontend/
```

Or per-package:
```bash
cd backend && npm start        # node server.js
cd frontend && npm run dev     # vite
cd frontend && npm run build   # tsc -b && vite build
cd frontend && npm run lint    # oxlint
```

There is no automated test suite (backend `npm test` points at a nonexistent `test-db.js`). Verify backend changes by hitting endpoints manually (e.g. via the health check `GET /health`) and verify frontend changes by running the dev server and exercising the flow in a browser.

Backend requires `backend/.env` (see `backend/.env.example`): `SUPABASE_URL`, `SUPABASE_KEY`, `JWT_SECRET`, `PORT` are the only hard requirements. Everything else is optional and degrades gracefully when blank: `GOOGLE_CLIENT_ID` (Google Sign-In), `RESEND_API_KEY`/`SMTP_*` (email, falls back to console logging), `UPSTASH_REDIS_REST_URL`/`_TOKEN` (shared rate limiting, falls back to in-memory), `BICTORYS_*`/`PAYTECH_*` (online payments, falls back to cash-only with a clear error), `API_PUBLIC_URL`/`APP_URL` (webhook/email callback URLs).

## Architecture

### Data layer: Supabase, not SQLite
Despite `README.md` describing SQLite, the backend now runs entirely on **Supabase (PostgreSQL)** via `@supabase/supabase-js` — `backend/database.js` exports a single `supabase` client (service-role key, RLS bypassed on the backend) used directly in every route file. `backend/supabase_schema.sql` is the source of truth for the schema: `clinics`, `users`, `patients`, `appointments`, `consultations`, `medications`, `stock_entries`, `prescriptions`, `prescription_items`, `lab_exams`, `payments`, `deposits`, `subscription_payments`, `payment_webhook_events`, `activity_logs`. `backend/migrate-data.js` was a one-off SQLite→Supabase migration script. `backend/mediclinic.db` is legacy/unused.

**Known gotcha — schema drift.** No session has direct DDL/migration access to the live Supabase database (only the REST API via `SUPABASE_KEY`), so every column/table added to `supabase_schema.sql` during a session is a *proposal* until a human runs the equivalent `ALTER TABLE`/`CREATE TABLE` by hand in the Supabase SQL Editor. This has repeatedly caused routes to 500 with `column "..." does not exist` (Postgres code `42703`) — including `GET /auth/me` itself, since it selects `users.work_schedule`. If you hit that error, check whether `supabase_schema.sql` already declares a column the live DB is missing before assuming a code bug. As of this writing the following migrations are declared in `supabase_schema.sql` but still need to be run by hand against the live DB:
```sql
ALTER TABLE users ADD COLUMN IF NOT EXISTS work_schedule JSONB DEFAULT NULL;
ALTER TABLE medications ADD COLUMN IF NOT EXISTS manufacturer TEXT;
ALTER TABLE medications ADD COLUMN IF NOT EXISTS unit TEXT;
ALTER TABLE clinics ADD COLUMN IF NOT EXISTS plan TEXT NOT NULL DEFAULT 'hopital' CHECK (plan IN ('starter', 'clinique', 'hopital'));
ALTER TABLE subscription_payments ADD COLUMN IF NOT EXISTS plan TEXT NOT NULL DEFAULT 'hopital' CHECK (plan IN ('clinique', 'hopital'));
ALTER TABLE clinics ADD COLUMN IF NOT EXISTS unlimited_staff BOOLEAN NOT NULL DEFAULT FALSE;
ALTER TABLE clinics ADD COLUMN IF NOT EXISTS suspended_by_platform BOOLEAN NOT NULL DEFAULT FALSE;
-- 17. Notifications Table (Super Admin broadcasts to clinic users — surfaced
-- in the notification bell alongside system-generated alerts, which are
-- computed live in backend/routes/notifications.js and have no row here)
CREATE TABLE notifications (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  created_by BIGINT REFERENCES users(id) ON DELETE SET NULL,
  title TEXT NOT NULL,
  body TEXT NOT NULL,
  target_all BOOLEAN NOT NULL DEFAULT FALSE,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

-- 18. Notification Clinics Table (join table — which clinics see a
-- target_all=false notification; left empty when target_all=true)
CREATE TABLE notification_clinics (
  notification_id BIGINT REFERENCES notifications(id) ON DELETE CASCADE NOT NULL,
  clinic_id BIGINT REFERENCES clinics(id) ON DELETE CASCADE NOT NULL,
  PRIMARY KEY (notification_id, clinic_id)
);

-- 19. Notification Reads Table (per-user read state). notification_id is
-- TEXT, not a foreign key to notifications(id), because it also tracks read
-- state for system-generated alerts like "sys-lowstock-42", which have no
-- row in the notifications table above and are recomputed on every request.
CREATE TABLE notification_reads (
  user_id BIGINT REFERENCES users(id) ON DELETE CASCADE NOT NULL,
  notification_id TEXT NOT NULL,
  read_at TIMESTAMPTZ DEFAULT NOW(),
  PRIMARY KEY (user_id, notification_id)
);
```

### Multi-tenancy
Every table carries `clinic_id`. Every query in every route **must** filter `.eq('clinic_id', req.user.clinicId)` — there is no database-level tenant isolation (RLS is bypassed by the service-role key), so this filter is the only thing preventing cross-clinic data leaks. When adding new routes or queries, follow the existing pattern in `backend/routes/*.js` exactly. The **sole deliberate exception** is `backend/routes/platform.js` — see Cross-clinic platform admin below.

### Auth & subscription gating
`backend/middleware/auth.js` exports `auth` and `checkRole(roles)`:
- `auth` verifies the JWT, attaches `req.user` (`{ userId, clinicId, role, ... }`), and also loads the clinic's subscription status. If the subscription is expired, all non-GET requests are blocked with `403 SUBSCRIPTION_EXPIRED` except billing (`/financials/subscription`, `/settings/plan`) and logout — this is the paywall enforcement point.
- `checkRole([...roles])` gates by role; `admin` always passes.
- Roles: `admin`, `doctor`, `secretary`, `pharmacist`, `lab_tech`, `manager`, `nurse` (see `frontend/src/contexts/AuthContext.tsx` for the canonical list). `role` is a free-text column (no DB-level enum/CHECK) — `checkRole([...])` is the only enforcement.
- Emails are normalized (`trim().toLowerCase()`) at every write/lookup point (register, login, Google auth, onboarding bulk staff-add, `settings.js` staff creation) — added after a real incident where a case-mismatch (mobile keyboard auto-capitalizing the first letter) or a copy-pasted trailing space silently failed login with a generic "Identifiants invalides", even with the correct password. Keep this normalization if you touch any of those handlers.

### Cross-clinic platform admin (`backend/routes/platform.js`)
A dashboard for the SaaS operator (not a clinic user) to see aggregate data across every clinic and manage support tickets — the only code in this repo that deliberately violates the multi-tenancy rule above (mostly read-only, `PUT /tickets/:id` is the one mutation, see Support tickets below). Gated by `backend/middleware/superAdminOnly`, which checks the caller's own email against `SUPER_ADMIN_EMAILS` (comma-separated env var) — **not** a `role` value, since there is no cross-clinic role concept in the `users` table. `GET /api/platform/overview` returns real aggregate stats (clinic counts, total users, this month's actual `subscription_payments` revenue — not clinics' own patient revenue, open ticket count), `/users` and `/subscriptions` return platform-wide lists. Frontend: `frontend/src/pages/PlatformAdmin/PlatformAdminPage.tsx` is a **wholly separate shell** with its own dark sidebar — deliberately not reusing the clinic `Sidebar`/`Header` (Patients/Rendez-vous/Ordonnances make no sense in a cross-clinic context), entered via a nav item in the normal `Sidebar` that's hidden unless `user.email` matches a client-side allowlist (UX hint only; the real boundary is the backend middleware). `Support` is a real functional section (see Support tickets below). The remaining sections (`Rapports`, `Sécurité`, `Config. système` nav items) are visually present but disabled/"Bientôt disponible" — there is no reporting, security, or system-config infrastructure in this codebase yet; don't fabricate data for them.

### Doctor/nurse work schedules & patient orientation
`doctor`/`nurse` users optionally carry a per-day work schedule (`users.work_schedule` JSONB — array of `{ day, off, start, end }`, `day` using JS `Date.getDay()` convention 0=Sunday..6=Saturday, `start`/`end` as `HH:MM`; a day can be `off: true` or have its own hours independent of other days) set on staff creation/edit in Settings. `backend/utils/schedule.js`'s `computeEffectiveAvailability()` derives the *effective* `availability_status` returned by `GET /auth/me` and `GET /settings/users`: outside that day's configured hours (or on an `off` day) it's always forced `'away'` (server-side, not just hidden in the UI); inside the window it's the manually-set value from `PUT /settings/availability` (also gated by schedule — rejected with 400 outside work hours). No schedule configured = always available (backward compatible with pre-existing accounts). This assumes server clock == clinic-local time, true because Côte d'Ivoire is UTC+0 year-round. "Orienter le patient" (redirect a patient to a doctor/nurse via an immediate `POST /appointments`) exists in two places: `PatientsPage.tsx` (secretary, right after creating a patient) and `PatientDetailPage.tsx` (doctor/nurse, any time, for referrals) — both pick from `GET /settings/users` filtered to active doctors/nurses.

### Route modules (`backend/routes/`)
One file per domain, each mounted in `backend/server.js` under `/api/<domain>`: `auth`, `patients`, `appointments`, `consultations`, `pharmacy`, `laboratory`, `financials`, `settings`, `deposits`, `webhooks`, `platform`, `cron`, `notifications`. Each authenticated handler follows the same shape: `auth` middleware → Supabase query scoped by `clinic_id` → write an `activity_logs` row for mutations → JSON response with French error/success messages. `platform` is the one exception to the `clinic_id`-scoping rule — see Cross-clinic platform admin below. Note: prescriptions are **not** their own route domain — `GET/POST /api/pharmacy/prescriptions[/:id]` lives inside `pharmacy.js` since dispensing is a pharmacy stock operation; the frontend's `pages/Prescriptions/OrdonnancesPage.tsx` calls this same endpoint. `deposits.js` handles the "Dépôt de garantie" (security deposit) feature — role-gated to `admin`/`secretary`/`manager`, tracks `held → refunded/deducted` status and separately `payment_status` for online payments (see Payments below); resolving a deposit requires `payment_status === 'paid'`, checked server-side, not just hidden client-side.

### Payments (`backend/services/payments/`, `backend/routes/webhooks.js`)
Two Mobile Money/card providers for Côte d'Ivoire, orchestrated with failover: **Bictorys** (`bictorys.js`) is primary, **PayTech** (`paytech.js`) is only tried if Bictorys fails at *initiation* (network/5xx/WAF) — never mid-flow after the buyer reaches a hosted payment page. `services/payments/index.js` exposes `initiateCheckoutWithFailover()` as the single entry point; both providers expose `isConfigured()` so checkout is cleanly disabled (with a clear French error, cash payments unaffected) when their env vars are blank.
- Three payment "types" share one flow, distinguished by a `<type>-<id>` reference generated at initiation and echoed back by the provider in webhooks: `sub-<id>` (subscription renewal, `subscription_payments` table), `pay-<id>` (patient payment, `payments` table), `dep-<id>` (deposit, `deposits` table). `webhooks.js`'s `fulfillEvent()` dispatches on the `<type>` prefix.
- Webhook routes (`POST /api/webhooks/bictorys`, `/paytech`) are mounted in `server.js` **before** the auth-adjacent middleware, deliberately outside the `auth` middleware — these are server-to-server calls authenticated by per-provider signature verification instead of a JWT. `server.js` captures `req.rawBody` via the `express.json`/`express.urlencoded` `verify` hook specifically so signatures can be checked against the exact bytes received.
- Idempotency: every webhook body is hashed and inserted into `payment_webhook_events` (`UNIQUE(provider, event_hash)`); a unique-constraint violation means "already processed" and the handler short-circuits. Fulfillment updates are also themselves idempotent (`UPDATE ... WHERE status = 'pending'`), so duplicate/replayed webhooks are safe either way.
- Amount verification (`amountMatches`) fails **closed**: a webhook claiming success with no reported amount is rejected, not trusted. PayTech gets a 5% tolerance (its fees are deducted before the reported amount); Bictorys must match exactly.

### Multi-tier subscription plans (`backend/utils/plans.js`)
`clinics.plan` (`'starter' | 'clinique' | 'hopital'`) drives feature gating clinic-wide; `PLANS` in `backend/utils/plans.js` is the single source of truth for pricing/limits, read by every route below — never hardcode a price or limit elsewhere.
- **Starter** (free, 7-day trial): max 3 active staff, roles restricted to `admin`/`doctor`/`secretary`, cash payments only. Activated instantly via `PUT /settings/plan` (no payment) — validated server-side against current staff count/roles before switching, so a clinic can't "downgrade" into a state that violates the new tier's limits.
- **Clinique** (9 000 FCFA/month): max 5 active staff, all roles, cash only.
- **Hôpital** (14 500 FCFA/month): unlimited staff/roles, adds Mobile Money (Wave/Orange Money/MTN) via Bictorys/PayTech.
- Enforcement points: `POST /settings/users` and `PUT /settings/users/:id` (staff-add and reactivation) and `POST /auth/onboarding`'s bulk staff-add all check `isRoleAllowedForPlan`/`isStaffLimitReached` before creating/reactivating a user. `POST /financials/checkout` (patient payments) and `POST /deposits` check `isPaymentMethodAllowed` before accepting a Mobile Money method. Unknown/legacy `plan` values degrade to `hopital` (the most permissive tier), never silently lock a clinic out.
- Paid-tier changes (upgrade, downgrade, or plain renewal) go through `POST /financials/subscription/checkout` with a `planId` in the body (defaults to the clinic's current plan if omitted); it prices from `PLANS[planId].price * months`, stores the target `plan` on the `subscription_payments` row, and validates the target tier's staff limit up front so payment isn't taken for a switch that would leave the clinic over-limit. The clinic's `plan` column is only actually switched by `webhooks.js`'s `fulfillSubscriptionEvent()` once the provider confirms payment — never at checkout-initiation time, same async-confirmation pattern as every other payment flow here. Starter is free and never goes through this endpoint (rejected with a message pointing at `PUT /settings/plan` instead).
- `middleware/auth.js`'s expired-subscription block allowlists `/settings/plan` alongside `/financials/subscription` and `/auth/logout`, so a blocked/expired clinic can still switch plans (including reactivating via the free Starter tier) without being locked out of the very endpoint meant to unlock it.
- Renewal reminder emails: `GET /api/cron/renewal-reminders` (mounted at `/api/cron`, gated by `CRON_SECRET` shared-secret header, wired into `vercel.json`'s `crons` for a daily 08:00 run) emails each clinic's admin at exactly 3 and 1 day(s) before `subscription_expires_at` — covers both the Starter trial countdown and paid-tier renewals off the same column. No dedup table; relies on the once-daily cron cadence plus exact-day matching to avoid double-sends.

### Support tickets (`support_tickets` table)
Single-message-plus-status tracker, not a threaded chat — a clinic admin files one ticket (`POST /settings/tickets`: subject, category, message) and can see their clinic's own ticket history (`GET /settings/tickets`) from Settings' "Support" tab. The SaaS operator sees every ticket across every clinic from Platform Admin's "Support" section (`GET/PUT /api/platform/tickets[/:id]`, gated by the existing `superAdminOnly` middleware — the same cross-clinic exception as the rest of `platform.js`), and changing a ticket's status fires an email to the clinic's admin via `sendTicketStatusEmail()` in `mailer.js` (fire-and-forget, doesn't block the operator's request). `GET /api/platform/overview` also returns `stats.openTickets`/`recentTickets` for the overview teaser card.

### Platform admin controls (`clinics.unlimited_staff`, `clinics.suspended_by_platform`)
Two Super-Admin-only manual overrides, independent of a clinic's billed plan: `PUT /api/platform/clinics/:id/staff-override` lifts the plan's staff *count* limit for one clinic (`isStaffLimitReached`'s third param) without touching its role restrictions (`isRoleAllowedForPlan` is untouched — unlimited accounts, not a role-gating backdoor); `PUT /api/platform/clinics/:id/suspend` is a kill switch blocking all non-GET requests for every user of that clinic (same enforcement point as `SUBSCRIPTION_EXPIRED` in `middleware/auth.js`, but with no billing-route bypass — paying doesn't lift a suspension, only a Super Admin reversing the toggle does). `PUT /api/platform/users/:id` lets a Super Admin activate/deactivate any user cross-clinic (self-lockout guarded, same pattern as `settings.js`'s own staff endpoint). **Self-lockout guard:** `/api/platform/*` routes are exempt from both the expiry and suspension checks in `middleware/auth.js` — otherwise a Super Admin whose own clinic is expired or suspended could be locked out of the one console able to fix it; safe because every `/api/platform` route is already gated by `superAdminOnly`. All three mutation endpoints write `activity_logs` against the *affected* clinic with `user_id` set to the acting Super Admin — the one place in this app where `activity_logs.user_id`'s own clinic and the row's `clinic_id` deliberately diverge (safe: no clinic-match constraint on that FK). Frontend: Platform Admin's Cliniques/Utilisateurs/Abonnements tables gained client-side search/filter, and Cliniques/Utilisateurs gained row actions (an expandable "Gérer" row for clinics, matching the pattern already used for support tickets in the same file).

### Notifications & Super Admin broadcasts
The Header's notification bell (`frontend/src/components/Header.tsx`, polled every 60s) merges two unrelated notification types into one feed via `GET /api/notifications` (`backend/routes/notifications.js`): **Super Admin broadcasts**, stored rows created by `POST /api/platform/notifications` (`backend/routes/platform.js`, Super-Admin-only, targets one/several/all clinics via the `notifications`/`notification_clinics` tables), and **system alerts**, which have no row of their own — they're recomputed live on every request from the same low-stock/near-expiry medication query the Dashboard already uses, and given a synthetic, stable id (`sys-lowstock-<medication id>`, `sys-expiry-<medication id>`) purely so read state can be tracked. This is why `notification_reads.notification_id` is `TEXT` rather than a foreign key to `notifications(id)` — it has to hold both real broadcast ids and these synthetic system-alert ids. Sending is owned entirely by `platform.js`; reading/merging/read-state is owned entirely by `notifications.js` — the two never share a route. Marking a notification read (`POST /api/notifications/:id/read`, `/read-all`) is exempted from `middleware/auth.js`'s suspension/expiry write-block (same pattern as `/api/platform`) since these routes only ever write the caller's own row in `notification_reads`, never clinic data — a suspended or expired clinic's users must still see and read notifications normally per the design spec.

### Frontend structure
- `App.tsx` is a manual tab router (no react-router) — auth state, onboarding gating, and the sidebar tab switch all live here as local state. Logged-out state is a separate `loggedOutTab` union (`'landing' | 'login' | 'register' | 'terms'`) from the authenticated `currentTab` string.
- Auth flow: unauthenticated → `LandingPage`/`AuthPage`/`TermsOfServicePage`; authenticated admin with no `clinic.address` → forced into `OnboardingPage`; otherwise the main tabbed dashboard renders. `AuthPage` supports email/password and Google Sign-In (`POST /auth/google`, verified server-side via `google-auth-library`; inert client-side if `GOOGLE_CLIENT_ID` is unset).
- `contexts/AuthContext.tsx` — user/clinic session, token stored in `localStorage` as `mediclinic_token`, calls `GET /auth/me` on mount to hydrate.
- `contexts/OfflineContext.tsx` — tracks `navigator.onLine`, queues actions to `localStorage` while offline, replays on reconnect (currently a simulated sync, not wired to real API calls).
- `contexts/NotificationContext.tsx` — `showToast(type, title, text)` app-wide toast notifications, auto-dismiss after 5s.
- `utils/api.ts` — typed fetch wrapper (`api.get/post/put/delete`) that attaches the JWT bearer token and normalizes errors to `{ status, error, code, message }`. `VITE_API_URL` env var overrides the API base; defaults to `http://localhost:5000/api` on localhost and `/api` otherwise (matches the Vercel rewrite).
- `pages/` mostly mirrors the backend route domains (`Patients/`, `Appointments/`, `Pharmacy/`, `Laboratory/`, `Accounting/`, `Deposits/`, `Settings/`, plus `Auth/`, `Dashboard.tsx`, `LandingPage.tsx`, `OnboardingPage.tsx`, `TermsOfServicePage.tsx`) — except `Prescriptions/OrdonnancesPage.tsx`, which is its own tab/page but has no matching backend domain (see above). `Profile/ProfilePage.tsx` similarly has no route file of its own; it drives `PUT /auth/password` in `auth.js` (change password, or set a first password for a Google-only account when `users.password_set` is still false — `currentPassword` only required when `password_set` is true) via the shared `components/PasswordChangeForm.tsx`.
- `components/` — `Sidebar`/`Header` (role-filtered nav + subscription-expiry banner), `MobileQuickActionsBar` (fixed bottom bar, mobile only), `PaymentCheckoutModal` (drives the Bictorys/PayTech hosted-checkout flow from any page that takes online payment), `PhoneInput` (wraps `react-phone-number-input` + `libphonenumber-js` for the CI-first country/dial-code picker used anywhere a phone number is captured), `AnimatedNumber` (count-up transition for dashboard/stat figures).
- Styling is plain CSS, not Tailwind: shared tokens/utility classes (`.btn`, `.card`, `.badge`, `.grid-cols-*`, `.landing-*`, `.auth-*`, HSL custom properties, light/dark via `[data-theme]`) live in `index.css`; individual pages mix those classes with inline `style={{}}` for one-off layout. Follow this pattern for new UI rather than introducing Tailwind or CSS modules. For mobile-width layout specifically, reuse `.app-page` (reduced padding under 640px), `.page-header-actions`/`.page-search-box` (header search box that shrinks instead of overflowing), and `.page-cta-btn` (smaller CTA buttons under 640px) — added across Patients/Pharmacy/Laboratory/Ordonnances/Deposits in a mobile audit; see `docs/mobile-audit-guide.md` for the full page-by-page findings before re-auditing a page that's already listed there as fixed or verified-clean.
- `frontend/index.html` carries the SEO/social surface for the public marketing pages: meta description, Open Graph/Twitter Card tags, a `SoftwareApplication` JSON-LD block, plus `frontend/public/robots.txt`/`sitemap.xml`. These currently reference a placeholder domain (`mediclinicpro.example`) pending the real production URL — grep for it before treating those as final. This only covers the "/" entry point; since `App.tsx` has no real per-route URLs (see above), logged-out sub-views (login/register/terms) aren't independently indexable or shareable — a known, deliberately-deferred limitation, not an oversight.

Larger features get a design spec (`docs/superpowers/specs/<date>-<feature>-design.md`, approved by the user before implementation) and/or an implementation plan (`docs/superpowers/plans/<date>-<feature>.md`, task-by-task) committed *before* the code lands. E.g. `2026-07-26-support-tickets-design.md`/`-support-tickets.md` spec out the support ticket system (see Support tickets above, now implemented). A committed plan describes intent at the time it was written — always check the actual code, not just the plan file, before assuming a described route/table exists or matches what was implemented. `2026-07-26-platform-admin-controls-design.md` specs out the per-clinic unlimited-staff override, suspension kill switch, and cross-clinic user deactivation (see Platform admin controls above, now implemented).

### Banani design imports
`.mcp.json` (gitignored) can hold a Banani MCP server for pulling designs via `mcp__banani__banani_get_selected_designs`. `.planning/banani/STATUS.md` tracks per-screen import status and decisions — check it before redoing work. Established pattern from that effort: prefer restyling/light polish over wholesale replacement when an existing page is already more functional than Banani's static mock (real data, role gating, working handlers), and never introduce fabricated stats, testimonials, or claims (e.g. data-residency claims, customer/adoption claims) that Banani's placeholder content includes — this has recurred across multiple Banani screens, not just the landing page.

### Deployment (Vercel)
`vercel.json` builds the frontend to `frontend/dist` and rewrites `/api/*` to the serverless function at `api/index.js`, everything else to `index.html` (SPA fallback). `framework` is forced to `null` to stop Vercel's autodetection from misidentifying the repo as Next.js. `installCommand` explicitly runs `npm install` in all three of the root, `backend/`, and `frontend/` — the root/frontend-only default silently skipped `backend/package.json`'s own dependencies (`@upstash/ratelimit`, `@upstash/redis`, `google-auth-library`, `libphonenumber-js`, `resend`), which used to crash every production request at cold start with an opaque `FUNCTION_INVOCATION_FAILED` and no indication which module was missing. In the Vercel serverless environment (`process.env.VERCEL` set), `backend/server.js` skips `app.listen` and only calls `initDb()` — see the bottom of that file. Environment variables (`SUPABASE_URL`, `SUPABASE_KEY`, `JWT_SECRET`, etc.) must be set in Vercel Project Settings, not read from `.env`. `.env` must be loaded (`require('dotenv').config(...)`) before any other require in `server.js`, since route/middleware modules read `process.env` at import time. `API_PUBLIC_URL` must be a public HTTPS URL in production — it's used to build payment-provider webhook callback URLs (e.g. PayTech's `ipn_url`). `backend/database.js` guards `createClient()` behind a check for `SUPABASE_URL`/`SUPABASE_KEY` instead of calling it unconditionally at import time — a missing/invalid Supabase config now fails every non-health request with a clear `503 SERVER_MISCONFIGURED` JSON error instead of crashing the whole function (including `/health`) before Express routes anything. The health check is registered at both `/health` and `/api/health` (`GET`, in `server.js`) since Vercel's `/api/(.*)` rewrite forwards the full original path — a bare `/health` route 404s in production even though it works in local dev where `server.js` listens on its own port; both paths are also exempted from the `SERVER_MISCONFIGURED` guard as liveness checks.

### CORS, security headers, and rate limiting
`server.js` applies `helmet()` (CSP and COEP disabled — the frontend is a separately-deployed SPA, not served from this origin) and allows `localhost:5173`/`127.0.0.1:5173`, any hostname ending in `.vercel.app`, and the production custom domain `mediclinicpro.com` plus its subdomains — matched against the parsed `URL(origin).hostname`, not a substring of the raw origin string (a bare substring check on `vercel.app` was spoofable, e.g. `https://evil.com/vercel.app`) — and, quietly, allows all origins whenever `NODE_ENV !== 'production'`. `/api/auth/login`, `/api/auth/register`, and `/api/auth/google` share `middleware/rateLimiter.js`'s `authLimiter`: a 100-requests-per-15-minutes-per-IP sliding window backed by Upstash Redis when `UPSTASH_REDIS_REST_URL`/`UPSTASH_REDIS_REST_TOKEN` are set (shared across serverless instances, required for this limit to mean anything on Vercel), falling back to in-memory `express-rate-limit` otherwise (per-instance only, resets on cold start). Keep all of this in mind when debugging cross-origin, CSP, or "too many requests" issues in French-language error responses.

### Email (`backend/utils/mailer.js`)
Three-tier fallback, checked in order: **Resend** (`RESEND_API_KEY`/`RESEND_FROM_EMAIL`) if set → **SMTP** via `nodemailer` (`SMTP_HOST`/`SMTP_USER`/`SMTP_PASS`/etc.) if set → otherwise logs the email content to the console. Don't assume SMTP is the primary path when reading this file — Resend is checked first.

### Phone numbers (`backend/utils/phone.js`, `frontend/src/components/PhoneInput.tsx`)
Shared validation: `validateAndNormalizePhone()` on the backend and `PhoneInput` (built on `react-phone-number-input` + `libphonenumber-js`) on the frontend, both defaulting to Côte d'Ivoire. Used anywhere a patient/staff phone number is captured (registration, patient records, onboarding).
